## 📖 개념 정리

### 1. Docker가 왜 필요한가?
개발할 때 흔히 겪는 문제:
> "내 컴퓨터에서는 되는데 서버에서는 안 돼요 🥲"

이런 문제가 생기는 이유는 개발 환경(OS 버전, 라이브러리 버전, 설정 등)이
사람마다, 서버마다 다르기 때문입니다.

**Docker**는 애플리케이션과 그 실행에 필요한 모든 환경(라이브러리, 설정, 코드 등)을
하나의 "이미지"로 통째로 포장해서, **어디서 실행하든 동일하게 동작하도록** 해주는 기술입니다.

### 2. 가상머신(VM) vs 컨테이너

| 구분 | 가상머신(VM) | 컨테이너(Container) |
|---|---|---|
| 실행 단위 | OS 전체를 가상화 | 프로세스 단위로 격리 |
| 무게 | 무겁다 (GB 단위) | 가볍다 (MB 단위) |
| 부팅 속도 | 느림 (분 단위) | 빠름 (초 단위) |
| 커널 | 자체 OS 커널 보유 | 호스트 OS 커널 공유 |

> 💡 핵심: VM은 "컴퓨터 자체"를 통째로 흉내내고,
> 컨테이너는 호스트 OS 커널을 공유하면서 프로세스만 격리시킨다.
> 그래서 컨테이너가 훨씬 가볍고 빠르다.

### 3. 이미지(Image) vs 컨테이너(Container)
- **이미지**: 애플리케이션 실행에 필요한 모든 것(코드, 런타임, 라이브러리, 설정)을 담은 "설계도" 또는 "붕어빵 틀"
- **컨테이너**: 이미지를 실제로 "실행"한 상태, 즉 붕어빵 틀로 찍어낸 "붕어빵"

같은 이미지로 컨테이너를 여러 개 실행할 수 있고, 각 컨테이너는 서로 독립적으로 동작합니다.

### 4. Docker의 기본 구조
- **Docker Client**: 우리가 터미널에 입력하는 `docker` 명령어
- **Docker Daemon(서버)**: 실제로 이미지를 관리하고 컨테이너를 실행하는 백그라운드 프로세스
- **Docker Registry**: 이미지를 저장/공유하는 저장소 (대표적으로 Docker Hub)

```
[Docker Client] --명령--> [Docker Daemon] --이미지 요청--> [Docker Registry(Docker Hub)]
                                |
                                v
                          컨테이너 실행
```

## 🧪 실습

### 1) 설치 확인
```bash
docker --version
```

### 2) 첫 컨테이너 실행해보기
```bash
docker run hello-world
```
이 명령어를 실행하면 아래 순서로 동작합니다.
1. 로컬에 `hello-world` 이미지가 있는지 확인
2. 없으면 Docker Hub(Registry)에서 자동으로 pull(다운로드)
3. 이미지를 기반으로 컨테이너를 생성 및 실행
4. 컨테이너 안에서 메시지를 출력하고 종료

### 3) 실행 결과 확인
```bash
docker images   # 다운로드된 이미지 목록 확인
docker ps -a    # 실행되었던(종료 포함) 컨테이너 목록 확인
```

---

## ✅ 배운 점 / 정리
- `docker run hello-world` 실행 시 Client → Daemon → Registry(Docker Hub) 흐름을 로그로 직접 확인함
- `docker images`로 로컬에 저장된 이미지 목록 확인. `hello-world` 외에 Docker Desktop이 내부적으로 쓰는 이미지(kindest/node, envoyproxy 등)도 같이 보인다는 걸 확인함
- `docker ps -a`로 종료된 컨테이너도 `Exited (0)` 상태로 기록이 남아있는 걸 확인함 → 이미지(설계도)와 컨테이너(실행 흔적)는 별개라는 걸 체감
